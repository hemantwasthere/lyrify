# The Overlay becomes a real titled window, reopening ADR-0006's non-activating panel

ADR-0006 made the Overlay a borderless, non-activating `NSPanel` specifically so it could never take keyboard focus — clicking play/pause must never steal focus from whatever the listener is doing elsewhere. A side-by-side against Spotify's own Mini Player showed that guarantee is exactly what's costing native resize behavior and a real close button: system traffic lights only render in color, and edge-resize cursors only behave natively, on a window that can become key — Lyrify's hand-rolled close dot and cursor stand-ins don't feel native because they aren't. The Overlay becomes a titled, `.closable`, `.resizable` window that can become key on click, trading away ADR-0006's "never steals focus" guarantee for a real close button and native resize behavior. The real close button is close-only — no miniaturize or zoom, since Lyrify has neither concept — repositioned out of AppKit's own title-bar strip into the existing hover-revealed chrome bar (same position, same per-Breakpoint visibility as the hand-drawn dot it replaces), and still routes through the same hide-not-quit path the menu bar's "Show Overlay" toggle already uses: clicking it hides the Overlay, it does not terminate the window.

## Considered Options

- **Keep ADR-0006's non-activating panel, hand-roll the missing affordances** — would have preserved the "never steals focus" guarantee, but leaves a close button that can never render in color (real traffic lights need a key-able window) and a cursor/behavior that's fundamentally an imitation of native windowing, not the real thing.
- **A titled, key-able window with a real, close-only button** (chosen) — gives up the "never steals focus" guarantee ADR-0006 established, in exchange for native traffic-light rendering and native resize behavior for free.

## Consequences

`OverlayWindow`'s `styleMask` changes from `[.borderless, .nonactivatingPanel, .resizable]` to `[.titled, .closable, .resizable, .fullSizeContentView]`; the `canBecomeKey`/`canBecomeMain` overrides that hard-coded `false` are removed, so the real close button can render in color when clicked. `titlebarAppearsTransparent = true` and `titleVisibility = .hidden` keep the window looking exactly as borderless as it does today — no visible native title-bar strip. The zoom button has no style-mask flag of its own to omit the way miniaturize does (it's gated by `.resizable`, which this window genuinely needs), so it's hidden directly instead.

`window.standardWindowButton(.closeButton)` is pulled out of its default title-bar position — there's only one such button for the whole window, unlike the two hand-drawn `hideButton`/`compactHideButton` instances it replaces (one per layout) — and reparented between Full Layout's overlaid bar and Compact Layout's stacked one as the Overlay's layout changes, landing at the same position with the same hover-reveal and per-Breakpoint visibility rules either one had.

The close button's action still resolves to the existing hide path (`OverlayWindow.onCloseRequested` → `OverlayController.hideOverlay()` → `visibilityPreference.isVisible = false`) rather than actually closing/deallocating the window — intercepted via `windowShouldClose(_:)`, the one choke point every close path funnels through — so "close" and "hide" stay the same single operation they always were; the status item's "Show Overlay" toggle is unaffected.

Clicking the Overlay can now make it (and Lyrify itself) key/active — the one real behavior change this ADR accepts, worth watching for in practice since it's the exact guarantee ADR-0006 existed to make.
